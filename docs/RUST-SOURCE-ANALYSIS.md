# Bounded Rust source checks

Kayfabe reads Rust tokens and recognizes a small set of client-builder expressions. It does not compile or execute Rust, install Cargo dependencies, expand macros or claim full Rust coverage.

## Initial checks

| Rule | Required evidence | Safe controls |
|---|---|---|
| `RUST-TLS-001`, CWE-295 | A resolved reqwest client builder explicitly sets `danger_accept_invalid_certs(true)` and then calls `build()` | Default validation, literal `false`, a later reset to `false`, unknown values or APIs, no build |
| `RUST-TLS-002`, CWE-297 | The same evidence for `danger_accept_invalid_hostnames(true)`, plus explicit `use_native_tls()` as the final selected backend | Rustls backend, unresolved/default backend, hostname validation enabled |

These are unsafe client-configuration candidates. They establish neither a reachable network request nor successful exploitation. Unknown settings invalidate that setting's proof; unknown builder methods invalidate the entire chain. A later literal value wins. One bounded immutable local handoff is supported as described below; helper returns and general variable flow are not followed. Imports through another import alias, including cycles, suppress semantic proofs rather than hiding a known terminating API.

Supported constructors are `Client::builder()` and `ClientBuilder::new()`, including `reqwest::blocking`. Simple, renamed and grouped `use` imports can resolve these types. Crate aliases must come from visible normal Cargo dependencies identifying registry reqwest. Optional, workspace-inherited, target-only, build-only, custom-source and conflicting dependencies are unresolved. Visible `.cargo/config` or `.cargo/config.toml` prevents an ownership claim because source replacement is not resolved. Local library names and normalized alias collisions are rejected. Missing or malformed metadata cannot establish ownership. Configuration outside the scan root, including machine and environment settings, is not inspected.

## Syntax and limits

The lexer handles ASCII and raw identifiers, lifetimes, character literals, escaped/raw/byte/C strings, nested comments and balanced token trees. Comments and literals never become executable API evidence. Lexical completion means tokenization succeeded within these limits; it is not a rustc syntax or type check.

The semantic subset consists of plain functions with flat statements and contiguous builder chains, including eagerly evaluated nested call arguments in the existing nonpropagating subset. Function generic parameters remain excluded. Return annotations may contain one flat nominal generic application with unit/path arguments, such as `Result<(), reqwest::Error>` or `std::result::Result<Client, reqwest::Error>`. Nested generic applications, where clauses and generic parameter types remain unsupported. This is structural syntax recognition: return names confer no API ownership, type identity or safety evidence. Parameter identifiers conservatively block matching constructor names, including names appearing only in parameter types; return paths do not create such bindings.

A separate propagation subset admits exactly one resolved constructor chain ending in immediate `.build()?;`, optionally assigned with `let [mut] name =`. Preceding statements may only be simple local declarations initialized with a single literal, number or non-raw boolean. Setter arguments in this subset are empty or a single literal, number or identifier, with an optional trailing comma; backend selectors require zero arguments, and arbitrary argument calls remain unsupported. The optional following expression is exactly `Ok(())`, optionally terminated by a semicolon, without claiming that `Ok` resolves to the standard Result variant. Other question operators, earlier unknown calls, multiple propagating chains, wrappers, post-question chaining and unwrap/expect followed by question stay unsupported. An unsupported token later in the function discards all its candidate findings and semantic counts. Independent functions retain their existing evidence. Ordinary nonpropagating build/unwrap/expect chains and their nested eager builder arguments retain their existing handling.

The local handoff subset admits one plain immutable `let owner = resolved_constructor().supported_setters(...);` immediately followed by one consuming `owner.supported_setters(...).build()` statement, optionally assigned to a plain local. The owner binding is not raw, mutable, destructured or type annotated, and cannot match a parameter. Its only executable local-name occurrences must be that binding and consuming receiver, across the complete function. Qualified path/member names are separate from reads of the owner. Aliases, references, moves, storage, reassignment, shadowing, clone/helper escape, another owner use or a second local builder invalidate this proof. Initializer and consumer share candidate-owned final flag/backend state. Evidence points at the final unsafe setter, including one in the initializer; a later literal false removes earlier unsafe evidence. Backend selection alone does not reset flags, and backend selectors require zero arguments.

Local setter arguments are empty or one literal/number/identifier, optionally followed by a comma. The only additional call expression is exact resolved `std::time::Duration::from_secs(decimal_integer)` with optional decimal underscores, using qualified paths or direct unambiguous imports; aliases through aliases, fake/locally shadowed standard paths, Cargo dependency/library identities named `std` and arbitrary calls are excluded. The owner cannot appear in arguments. This is token-level identity and effect restriction, not general type checking. Unknown flag values yield no unsafe or safety proof. Before the pair only the same literal declarations as the direct propagation subset are admitted; afterward only its optional exact `Ok(())` tail is admitted. Calls or effects elsewhere reject the local proof.

The consuming terminal may be immediate `.build()?;`, ordinary `.build();`, or build followed by empty `unwrap()` / literal-argument `expect()` and a semicolon. The question form retains one complete-function terminal proof: it does not admit unrelated questions, another build question, unknown calls, post-question chaining or unwrap followed by question. All new local candidates commit after the complete owner/statement/terminal proof. Failed local analysis leaves independently supported existing nonpropagating direct chains and eagerly evaluated nested chains intact; existing global effect/ownership/budget guards still apply. A fully proved safe reset counts once as a resolved chain; unsupported local state adds no new chain credit. Legacy non-question function admission credit is retained separately and does not prove that an unsupported local handoff completed.

Branches, loops, early returns, await, closures and nested blocks remain excluded. An async function qualifier alone was already supported and adds no async execution proof. Selected known terminating APIs (`exit`, `abort`, `panic_any`, `resume_unwind`, `handle_alloc_error`) and their direct import aliases exclude the containing function. Visible active or unresolved never-returning function types (`-> !`) suppress project semantic proofs; cfg-proven-absent items do not. This is not general helper reachability analysis. A [bounded module and cfg layer](RUST-MODULES-CFG.md) resolves supported structural paths and proven configuration predicates before applying these checks. Macro expansion, unknown attributes and unresolved namespace effects still prevent semantic proofs in affected scopes.

Limits are 1 MiB and 100,000 tokens per file; 128 nested delimiters or block comments; 255 raw-string hashes; and 4,096 files, 32 MiB of source, 32 MiB of manifests and 400,000 tokens per project. A final file can reach the per-file token cap before the aggregate check stops further input. Budget failures produce fixed diagnostic codes, with no target text. Any missing input that could affect ownership prevents semantic proofs.

The shared one-million-token analysis work budget also covers the local occurrence ledger, statement/terminal traversal and additional setter/path/argument walks, including rejected candidates and repeated module contexts. Physical constructor positions and function-item sets prevent counting the two local segments or repeated contexts twice. Exhausted work suppresses findings and semantic counts rather than committing partial candidates. The local subset does not perform borrow checking, general ownership, branch analysis or helper/type inference.

## Reading coverage

`coverage.source.rust` reports eligible/tokenized files, discovered/analyzed functions, resolved builder chains and diagnostic counts. Function counts describe the supported checks, not complete parsing, taint coverage or vulnerability recall. Files omitted by a budget are reported separately. Excluded tests do not enter the coverage denominator.

Rust always keeps `coverage.source.status` incomplete and fails an explicitly required complete-coverage gate. Cargo inventory and advisory coverage remain separate. A passing severity gate with zero Rust findings is not a clean security assessment.

## Hermes and remaining gaps

The immutable Hermes original/fixed pair is previously exposed development data with no frozen vulnerability answer key. Its source exercises raw strings, lifetimes, attributes, FFI and macros. It receives no accuracy score or automated credit for manual findings. The initial checks add no Hermes finding: its reqwest builders do not explicitly disable certificate or hostname validation.

The original aggregate body-admission concern remains a manual review question. Following the fixed variant's shared semaphore, permit lifetime, host/auth guards and response stream requires control flow and ownership analysis beyond this phase. Finite `to_bytes` limits, `unsafe`, separate arguments to a fixed executable, loopback/listen settings and an inbound self-signed certificate are not vulnerability evidence by themselves. Cross-file taint, authorization intent, SSRF origin control and upstream deadlines remain gaps.

Eight scanner-owned vulnerable/fixed corpus pairs provide Rust regression coverage only, including two flat Result/terminal-build-question pairs and two immutable local-handoff pairs. They are not independent evaluation data. Established benchmarks and supplied applications retain their separate labels and policies.

See [the module/cfg measurements and review summary](RUST-MODULES-CFG-RESULTS.md) for the current scanner version, unchanged benchmark decisions and Hermes coverage counts. The [initial source measurements](RUST-SOURCE-RESULTS.md) remain historical evidence.
